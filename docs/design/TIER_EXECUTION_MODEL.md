# Tier 执行模型讨论记录

> 日期：2026-05-08
> 背景：mem0ress 规范自洽性审查过程中，对 Tier 0/1/2/3 的执行主体和持久性问题进行深入讨论

---

## 1. 核心问题

**问题 1**：Tier 0/1/2/3 是否都需要 Agent 执行？

**问题 2**：Judge Agent 是否需要持久保活？

**问题 3**：在不同宿主环境下（Claude Code / Hermes / 企业级），检验的执行模式是否应该不同？

---

## 2. Tier 的本质分类

| Tier | 检查内容 | 本质 | 是否需要 LLM |
|------|---------|------|-------------|
| **Tier 0** | 约束违反检查 | 模式匹配 / 规则判断 | **不需要** |
| **Tier 1** | Todo 完成 + 子任务关闭 | 文件系统状态查询 | **不需要** |
| **Tier 2** | Requirements 满足检查 | **混合**——规则检查 + 边界判断 | **部分需要** |
| **Tier 3** | 语义对齐 | 自然语言理解 + 判断 | **需要** |

**结论**：
- Tier 0/1 是纯机械的，不需要 LLM
- Tier 3 是纯判断的，需要独立 Agent
- Tier 2 取决于 Requirements 的设计质量——如果设计得当，应该是机械的

---

## 3. Judge Agent 的持久性问题

### 3.1 Judge Agent 的工作性质

- **任务**：语义对齐判断（Picture vs Artifact）
- **触发**：按需（不是每轮次）
- **输入**：Picture + 实际产出
- **输出**：aligned / deviation + 原因
- **每次验证是独立的**，不需要跨验证的状态

### 3.2 核心洞察

> Judge Agent 是**任务作用域**的，不是**系统作用域**的。

不需要跨验证的持久状态，不需要预热，不需要上下文保持。

### 3.3 三种执行模式

| 模式 | Judge 生命周期 | 适用场景 | 状态需求 |
|------|--------------|---------|---------|
| **临时 Agent** | 每次 spawn，用完销毁 | Claude Code（默认） | 无 |
| **会话级 Agent** | 首次请求时冷启动，会话内复用 | Hermes | 轻量（当前任务上下文） |
| **常驻服务** | 长期运行 | 企业级 | 审计日志、速率限制、并发控制 |

### 3.4 结论

**Judge Agent 不需要持久保活**。

理由：
1. 验证是独立的，每次验证只看当前任务的 Picture + Artifact
2. 语义判断无状态——输入输出都写入文件系统，Judge 不需要保留任何东西
3. 轻量优先——mem0ress 定位是轻量级认知工具
4. 让宿主决定——是否常驻是宿主环境的选择，不是 mem0ress 规定的

## 4. 分层执行模型

### 4.1 不同宿主环境的威胁模型

| 宿主环境 | 检验执行主体 | 作弊动机 | 可信度要求 |
|---------|------------|---------|-----------|
| **Claude Code** | 主 Agent 自己 | 无（本地单次会话） | 低 |
| **Hermes** | 主 Agent 或子 Agent | 极低（团队信任） | 中 |
| **生产级企业** | 独立验证服务 | 高（可能有利益冲突） | 极高 |

### 4.2 分层执行模型

```
┌─────────────────────────────────────────────────────┐
│  mem0ress 接口契约（跨宿主通用）                       │
│  - Tier 0/1/2/3 的触发时机                           │
│  - Tier 0/1/2/3 的输入输出格式                        │
│  - 检验结果对 Agent 的呈现方式                        │
└─────────────────────────────────────────────────────┘
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   ┌─────────┐      ┌─────────┐      ┌─────────┐
   │  L0     │      │  L1     │      │  L2     │
   │ 内省模式 │      │ 分离模式  │      │ 隔离模式  │
   └─────────┘      └─────────┘      └─────────┘
```

| 模式 | Tier 0 | Tier 1/2 | Tier 3 | 适用场景 |
|------|--------|---------|--------|---------|
| **L0：内省模式** | mem0ress 发起点 | 主 Agent 自检 | 主 Agent 调用外部 LLM | Claude Code、探索性任务 |
| **L1：分离模式** | mem0ress 发起点 | 主 Agent 调 Harness 接口，结果写入文件系统 | 独立 Judge Agent 在沙箱中执行 | Hermes、标准 Agent 系统 |
| **L2：隔离模式** | mem0ress 发起点 | 独立 Harness 服务验证，结果防篡改 | 独立 Judge 服务，完整审计日志 | 企业级应用、高危任务 |

### 4.3 Tier 0 的特殊性

> Tier 0 是"发起点"，不是"执行主体"。

- **发起点在 mem0ress**：每轮次结束自动触发
- **恢复点在宿主**：让度请求的路由和处理由宿主负责

## 5. 机械检查 vs LLM Agent

### 5.1 机械检查的典型场景

- "代码是否包含明文密码" → 搜索正则 `password\s*=\s*['"]`
- "Todo 1 是否完成" → 检查文件是否存在
- "子任务是否全部关闭" → 检查目录是否存在
- "Access Token 有效期 ≤ 1 小时" → 检查代码中的配置值

这些是**确定性操作**，不需要 LLM。

特性：
- 延迟低（毫秒级）
- 成本低（接近零）
- 可信度高（结果确定）
- 无判断空间（不存在"语义歧义"）

### 5.2 需要 LLM 的场景

- "产出是否达到 Picture 描述的成功状态" → 需要理解自然语言图景和实际产出的语义关系
- "界面是否美观" → 无法用规则定义
- "用户是否感到满意" → 需要主观判断

### 5.3 Tier 2 的边界

**关键问题**：如果 Requirements 设计得当，Tier 2 应该是机械的，还是仍需要 Agent？

**分析**：
- 如果 Requirements 是规则式的（"支持 OAuth 2.0"、"Access Token 有效期 ≤ 1 小时"），Tier 2 是机械的
- 如果 Requirements 是模糊的（"代码可读性好"、"接口设计合理"），它就不符合规范——这样的 Requirements 应该被拒绝或重新设计

**结论**：
> 如果规范要求 Requirements 必须可自动化检验（"是否可自动化检验"是 Requirements 的质量判断标准），那么 Tier 2 应该是机械的，不需要 LLM。

## 6. 防止作弊的机制

### 6.1 核心问题

如果 Tier 0/1/2 由主 Agent 执行，主 Agent 能否跳过检查直接标记完成？

### 6.2 不同环境的分析

| 环境 | 主 Agent 作弊可能性 | 防范机制 |
|------|-------------------|---------|
| **Claude Code** | 低（用户直接观察） | 依赖 Agent 的自我约束 |
| **Hermes** | 中（团队内部） | 检查结果写入文件系统，主 Agent 无法篡改 |
| **企业级** | 高（绩效利益） | 独立验证服务，完整审计日志 |

### 6.3 分层防线

```
┌─────────────────────────────────────────────┐
│  第一层：检查结果写入文件系统                 │
│  - 主 Agent 调用检查接口                     │
│  - 结果直接写入文件，不经过主 Agent 内存     │
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│  第二层：Harness 是内置组件                  │
│  - Tier 0/1/2 由 Harness 内置执行           │
│  - 不是主 Agent 调用的外部服务               │
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│  第三层：让度机制                            │
│  - 主 Agent 无法自行判断时发起让度           │
│  - 由人或其他 Agent 最终仲裁                 │
└─────────────────────────────────────────────┘
```

## 7. 架构缺口分析

### 7.1 已识别的缺口

**缺口 1**：spec.md 定义了"Tier 0/1/2/3 检查什么"，但没有定义"谁来检查"。

**缺口 2**：spec.md 定义了"让度的触发条件"，但没有定义"让度的实现方式"。

**缺口 3**：spec.md 定义了"Harness Engine"，但没有明确它是 mem0ress 内置还是宿主提供。

### 7.2 需要明确的决策

| 问题 | 选项 |
|------|------|
| **Tier 1/2 的执行主体** | A）主 Agent 自检；B）独立 Harness 服务 |
| **让度的实现方式** | A）spawn 子 Agent；B）调用外部服务；C）等待人工介入；D）宿主自定义 |
| **Harness Engine 的归属** | A）mem0ress 内置（标准实现）；B）宿主提供（可替换） |
| **Judge Agent 的持久性** | A）按需 spawn（默认）；B）常驻服务（企业级可选） |

## 8. 方向建议

### 8.1 方案 A：轻量方案

- mem0ress 只定义接口契约，执行细节全留给宿主
- 优点：简单通用，适合 Claude Code 等轻量场景
- 缺点：企业级用户可能认为缺乏架构约束

### 8.2 方案 B：标准方案

- mem0ress 内置标准实现（L0 内省模式），宿主可替换
- Tier 0/1/2 由内置 Harness 执行，Tier 3 由 Judge Agent 执行
- 优点：提供开箱即用的完整方案
- 缺点：增加复杂度

### 8.3 方案 C：混合方案（推荐）

- **核心机制内置**（Tier 0/3 的触发时机和接口契约）
- **执行层可替换**（Tier 1/2 的实现由宿主决定）
- **分层执行模型**（L0/L1/L2 由宿主选择）

优点：保持轻量，同时满足不同宿主的需求。
