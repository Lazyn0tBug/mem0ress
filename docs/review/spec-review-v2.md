# mem0ress 规范评审报告（2026-05-09 第二版）

**评审日期：** 2026-05-10  
**评审框架：** scientific-critical-thinking（规范评审扩展）  
**评审范围：** spec.md（v3.6）、arch.md（v0.1）、design.md  
**评审维度：** 内容、解构、逻辑、颗粒度、创新性、一致性  

---

## 一、内容（Content）

### 1.1 整体评价

mem0ress 的内容层在"问题定义"和"理念构建"上相当扎实。第一章通过三个结构性问题（数据汤困境、意图迷失、大模型之上的大模型）精准定位了现有 Agent memory 系统的痛点。第二章的四个洞察推导链（洞察一→洞察二→洞察三/四）有明确的依赖说明，不是简单罗列——这一点在架构规约中非常难得。

**核心洞察的有效性：**

双平面正交设计（状态平面 vs 数据平面）是 spec 最实质性的创新。状态平面强制挂载（回答"我在哪"）、数据平面按需展开（回答"操作什么版本的代码"）的分离设计，有认知效率上的明确理由，且在工程上有可操作性。Picture 作为绝对锚的设定也切中传统软件工程的盲区——测试用例通过 ≠ 目标达成。

### 1.2 内容缺口

**P0 缺口：**

1. **让度模型缺失（P0）。** spec 7.4 节和 arch 多次提到"让度"，但让度的语义边界从未被定义：什么情况下 Agent 必须让度给人？什么情况下 Agent 可以自主决策？这个边界不定义，cognitive alignment plane 的"对齐"就缺少了最关键的一环——人在回路中的边界。

2. **Judge Agent 行为规范缺失（P0）。** arch.md 将 Judge Agent 定位为"Tier 0/1/2/3 执行器"，但 Judge Agent 本身的行为规范（如 prompt 模板、决策逻辑、输出格式）在规范中完全缺失。`{task_id}-judge.md` 文件的内容结构从未被定义，模板只在文件树中出现，没有实际内容。

3. **report.md 和 verification_history 关系悬空（P0）。** spec 7.3 提到检验结果写入 `report.md`，516 行提到验证历史追加到 `verification_history` 字段，但模板（538-569行）的 frontmatter 中没有 `verification_history` 字段，`report.md` 也不在任何附录中定义。arch.md 的文件树包含了 `report.md`，但它的内容结构和写入约束也未定义。

4. **认知科学来源悬空（Critical）。** 2.2 节末尾提到"目标导向行为理论（Goal-Directed Behavior）和约束满足网络（Constraint Satisfaction Networks）"，2.3 节提到"人类长期记忆以事件（Event）为单位组织"，但都是悬空引用——无作者、无论文、无页码。如果规范要成为"可独立引用的理论锚点"（spec 原话），悬空的理论引用会削弱其权威性。

**P1 缺口：**

5. **无完整执行示例。** 全篇没有从任务创建到检验到完成的完整案例。Picture 填写质量判断标准（"是否可感知"）只有反面示例，没有正面示例。规范对于"新手如何第一次写出合格的 Picture"没有可操作的参照。

6. **manifest status 的 truth 地位未澄清。** Session 是 append-only 的历史快照，Manifest 是当前状态，但如果 Manifest 在运行时被更新（如 `complete_task()` 修改了 status），Session 快照和 Manifest 谁是当前 truth？spec 没有明确回答这个问题。

## 二、解构（Document Structure）

### 2.1 三文档分工问题

**spec.md、arch.md、design.md 的分工存在重叠和遗漏：**

| 主题 | spec | arch | design | 问题 |
|------|------|------|--------|------|
| Tier 0 自动触发 | 7.3 节说"宿主在轮次结束后自动触发" | 4.1 说"Tier 0 在 verify() 链路内部自动执行" | 3.3 说"Tier 0/1/2 由 Judge Agent 自动执行" | 三个文档对 Tier 0 触发机制的描述不完全一致 |
| 让度模型 | 7.4 节简单提到"让度执行，触发条件由宿主定义" | 未定义 | 3.6 节说"让度的持有点"但没有展开 | 让度在三文档中都是悬空的 |
| Judge Agent | 附录 A 节点表中出现，无细节 | 2.4 节有状态机和管理，但没有 prompt/行为规范 | 3.1 节有生命周期，没有行为规范 | Judge Agent 的定义分散在三处，都不完整 |
| verification_history | 516 行提到，模板中没有 | 未定义 | 未定义 | 这个字段到底存不存在？ |

**关键问题：spec.md 第8章"暂无内容"（789行）仍然存在。** 上一版评审已经指出这个占位问题，但 v3.6 版本仍未处理。

### 2.2 章节依赖关系

spec.md 的 2（洞察）→ 3（理念）→ 4（准则）→ 5（概念）→ 6（数据模型）→ 7（流程）看起来是线性依赖，但实际存在逆向引用：

- 5.1 说"第二章（洞察二）已完整阐述了理论基础，本节聚焦实际使用时的操作指南"——这是正向引用。
- 5.2 说"spec 定义组装的时机和职责边界，arch 定义具体的组装机制"——这引入了 arch.md，违反了"规范不引用实现文档"的单向依赖原则。
- arch.md 第 9 行说"规范不引用本文档，依赖方向单一"，但第 8 节的依赖关系图是单向的（spec → arch），arch 不引用 spec。这个约定在 arch 的正文中被遵守了。

## 三、逻辑（Logic）

### 3.1 核心逻辑问题

**问题 1："无隐藏状态"原则存在自我违反（P0）。**

spec 4.3 承诺"零中介：系统完全建立在目录树+纯文本之上，没有任何私有格式或隐藏状态"。但 5.2 节描述状态平面时，说它是"由认知数据模型按需组装的产物"——这里的"认知数据模型"（Plane Assembler 的代码逻辑）本身就是一个隐藏的组装机制。Manifest 是文件，但状态平面是运行时装配出来的。当两者内容不一致时，谁是 truth？spec 没有回答这个矛盾。

**问题 2：Tier 0 自动触发 vs 无后台守护的矛盾（上一版已识别，v3.6 部分修复但未完全解决）。**

spec 7.3 说"检验由宿主在轮次结束后自动触发"。arch.md 4.1 说"宿主系统自动调用 snapshot_session"。但 design.md 3.6 说"mem0ress 自身没有后台守护进程"。这三个描述放在一起：

- 如果"宿主"就是指 OpenClaw Event Loop，那"自动触发"是宿主的责任，不是 mem0ress 的责任——这个矛盾可以解决。
- 但 spec 7.3 的 mermaid 图（第 629 行）和 arch.md 4.1 的 sequence diagram 都没有体现这个责任转移。图中显示的是"系统自动触发"，没有明确标注"由宿主触发"。

**问题 3：Judge Agent 状态机与 Task 状态机混淆（P0）。**

arch.md 2.4 节定义了 Judge Agent 的状态机：`created → ready → verifying → completed → destroyed`。spec.md 附录 A 定义了 Task 的状态机：`CREATED / IN_PROGRESS / VERIFYING / COMPLETED / ABANDONED`。

两者都包含 `VERIFYING` 状态，但含义不同：
- Task 的 `VERIFYING` 是生命周期中的中间状态（检验进行中）。
- Judge Agent 的 `verifying` 是其执行检验时的内部状态。

arch.md 2.4 节说"Task 进入 VERIFYING 时 Judge Agent 被唤起"，这意味着两个状态机是耦合的。但 arch 没有说明：如果检验过程中 Judge Agent 遇到错误（状态机进入 `error`），Task 的 `VERIFYING` 状态如何处理？这个耦合是脆弱的。

**问题 4：Tier 3 启用判断逻辑悬空（P0）。**

spec 7.3 说"Tier 3 由 Agent 根据任务属性决定是否启用"，列举了四种情况（主观判断、语义歧义、高危、显式请求）。但"根据任务属性"是一个主观判断——谁来判定"这个任务是否涉及主观判断"？如果 Agent 判断"不需要 Tier 3"，但实际产出与 Picture 有语义偏差，谁来发现这个遗漏？这个悬空使得 Tier 3 的实际触发不可预测。

**问题 5：让度模型的语义边界未定义（P0）。**

spec 7.4 提到"让度执行"和"让度执行的触发条件由宿主定义"，但：
- 让度请求长什么样？（格式？内容？）
- Agent 发起让度后处于什么状态？（暂停？继续？）
- 人类响应后执行路径是什么？（回到哪个节点？）
- 什么情况下 Agent 必须让度？什么情况下可以自主决策？

这四个问题在规范中完全没有被回答。design.md 3.6 提到"让度的持有点：Tier 0 检测到约束违反且主 Agent 无法自行修复时，Agent 发起让度请求并同步等待外部响应"，但这只是触发时机，不是完整的让度模型。

### 3.2 因果推理链评估

mem0ress 的核心推导链：

```
洞察一（目标属性）→ 洞察二（PRC 框架）→ 洞察三（Task 锚点）+ 洞察四（双平面正交）
```

这个链条在逻辑上是自洽的。但存在两个问题：

1. **洞察三和四的推导结论过于宽泛。** 从"三要素需要一个载体"推导出"任务作为认知单元"是合理的。但 spec 说"任务（Task）作为信息的组织单元，恰好对应了这个认知模型"——这个类比缺乏具体证据。人类记忆以事件为单位，但 Task 和 Event 之间的映射并不天然成立，需要更多论证。

2. **双平面正交的实现理由依赖于论断而非证明。** spec 说"如果每次获取状态都要同时加载数据版本和执行进度，认知负载翻倍"——但这个"翻倍"是论断，没有数据或案例支撑。

## 四、颗粒度（Granularity）

### 4.1 过粗（P0）

1. **Judge Agent 没有行为规范。** "Judge Agent 执行 Tier 0/1/2/3 检验"——但 Judge Agent 是什么？它的 prompt 是什么？它的输出格式是什么？它如何做决策？这些信息全部缺失。如果 mem0ress 是可执行的框架，Judge Agent 的行为规范是不可或缺的。

2. **让度模型没有定义。** 见 3.1 节问题 5。

3. **report.md 和 verification_history 未定义。** 见 1.2 节问题 3。

### 4.2 过细（P2）

1. **5.1 节的"Who defines"表格（364-368行）。** 描述了 Picture/Requirements/Constraints 分别由谁定义，颗粒度过细。这类操作指南更适合放在用户手册或实现指南中，不适合放在"架构规约"里。

2. **附录 A 的节点表过于详细。** "Turn N"的格式说明（如 1.1, 1.2, 2.1 体现嵌套关系）更适合放在模板参考中，不适合放在附录的状态定义里。

## 五、创新性（Innovation）

### 5.1 真正创新的部分

1. **双平面正交设计是 mem0ress 最核心的创新。** 状态平面强制挂载、数据平面按需展开的分离设计，有认知效率上的明确理由，且在工程上有可操作性。这个设计直接回应了"数据汤困境"的核心问题。

2. **"Picture 作为绝对锚"区分了"满足需求"和"达成目标"。** 这个洞察对 Agent 的完成判断有实际意义——防止 Agent 陷入"勾选心态"。

3. **SSOT + 绝对覆写的设计在避免认知歧义上有实质作用。** 与传统的向量检索+合并策略相比，这个设计更简洁、更可预测。

### 5.2 创新性不足的部分

1. **"目标锚定"、"认知而非记忆"等理念是对现有认知科学概念的重新包装。** spec 没有提供 mem0ress 独有的理论贡献。洞察一（二）实际上是认知科学中已有的概念（目标导向记忆、情景记忆），但 spec 将其包装为"洞察"而没有明确引用。

2. **分形树状结构在实际落地时的鲁棒性未验证。** spec 说"父任务完成以所有子任务完成为前提"，但在多仓库开发场景下，子任务的完成状态如何跨仓库保持一致？当父任务和子任务处于不同 git 仓库时，"目录深度表达依赖关系"的物理化依赖设计是否会失效？这些问题没有讨论。

## 七、补足优先级

### P0（规范不可运行的缺口）

| # | 问题 | 建议 |
|---|------|------|
| P0-1 | 让度模型未定义 | 在 spec 第 7.4 节增加让度模型定义：让度请求格式、Agent 暂停状态、恢复路径、必须让度 vs 可自主决策的边界 |
| P0-2 | Judge Agent 行为规范缺失 | 在 spec 附录增加 `{task_id}-judge.md` 的模板定义，包括 prompt 结构、决策逻辑、输出格式 |
| P0-3 | report.md 和 verification_history 关系悬空 | 统一验证结果的存储：明确 report.md 是临时文件（每轮覆写）还是持久化文件；verification_history 是否存在，如果存在则添加到 Manifest 模板 |
| P0-4 | "无隐藏状态"自我违反 | 澄清状态平面的 truth 来源：当 Plane Assembler 组装的状态平面与 Manifest 文件内容不一致时，以 Manifest 为准 |

| # | 问题 | 建议 |

## 八、总结评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 内容 | 8/10 | 洞察深刻，问题定义精准，但认知科学来源悬空 |
| 解构 | 6/10 | 三文档分工基本合理，但存在重叠和遗漏，第 8 章占位问题未解决 |
| 逻辑 | 5/10 | 核心推导链清晰，但存在 5 个关键逻辑缺口（无隐藏状态自我违反、Tier 0 触发机制、状态机混淆、Tier 3 悬空、让度模型缺失） |
| 颗粒度 | 6/10 | 核心机制过粗（Judge Agent、让度模型、report.md），辅助描述过细（谁定义表格） |
| 创新性 | 8/10 | 双平面正交和 Picture 锚点是实质性创新，"目标锚定"等理念的原创性不足 |
| 一致性 | 5/10 | 存在 8 处以上可定位的不一致，manifest truth 地位、verification_history 字段存在性、report.md 定义等关键问题未解决 |

**核心结论：**

spec.md 的理念层（第二章、第三章）和问题定义层（第一章）已经相当成熟。双平面正交设计是 mem0ress 最核心的创新，有认知效率上的明确支撑。但在向可执行规约转化的过程中，四个 P0 缺口（让度模型、Tier 3 悬空、report.md/verification_history 关系、"无隐藏状态"自我违反）必须被解决，否则规范无法成为真正的"可运行架构规约"。
