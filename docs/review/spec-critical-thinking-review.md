# spec.md 规范评审报告

**评审日期：** 2026-05-09  
**评审框架：** scientific-critical-thinking  
**评审维度：** 内容、解构、逻辑、颗粒度、创新性、一致性  

---

## 一、内容（Content）

### 优势

- **问题诊断精准。** "数据汤困境"、"意图迷失"、"大模型之上的大模型"三个结构性问题直击当前 Agent memory 系统的痛点。
- **四个洞察的推导链清晰。** 洞察一→洞察二→（洞察三/洞察四）的依赖关系有明确说明，不是简单罗列。
- **Picture 作为绝对锚的设定有说服力。** "测试用例通过 ≠ 达成目标"的区分切中传统软件工程的盲区。

### 缺口

1. **认知科学来源悬空（Critical）。** 2.2 节末尾提到"目标导向行为理论（Goal-Directed Behavior）和约束满足网络（Constraint Satisfaction Networks）"，2.3 节提到"人类长期记忆以事件（Event）为单位组织"，但都是悬空引用——无具体作者、无论文、无页码。规范本身承认"认知科学来源 defer 到最后统一解决"，但这意味着当前的"洞察"章节其实缺少支撑它成为"洞察"的具体证据。作为规范，这个层级的悬空引用会削弱规范本身的权威性。

2. **无实际完整案例。** 全篇没有一处完整的任务示例（从创建到检验到完成的全流程），只有片段性的 OAuth 登录描述（7.3 节）。Picture 填写质量判断标准（"是否可感知"）缺乏正面示例，只有反面的"实现路径 vs 成功状态"。规范对于"新手如何第一次写出合格的 Picture"没有提供可操作的参照。建议在第7章末尾增加一个完整的五步示例（任务创建→Todo 拆解→Tier 1 检验→Tier 2 检验→状态更新）。

## 二、解构（Document Structure）

### 结构概览

```
1. 综述（背景/定位/核心解法）
2. 核心洞察（4个洞察，含推导关系）
3. 设计理念（4个理念）
4. 工程准则（3个准则）
5. 概念（认知三要素/双平面）
6. 文档数据模型
7. 逻辑与流程设计
8. 暂无内容 ← 问题
9. FAQ
附录A（状态与节点）
附录B（模板参考）
```

### 问题

1. **章节之间的依赖关系不清晰。** 2（洞察）→ 3（理念）→ 4（准则）→ 5（概念）→ 6（数据模型）→ 7（流程）看起来是线性依赖，但实际存在逆向引用。例如 5.1 指引读者去 2.2 看理论依据，5.2 又说"spec 定义时机/边界，arch 定义机制"——但 spec 本身就有 arch 引用，这是 spec/arch 耦合，不是单向的 spec 定义。

2. **章节 8 "暂无内容"不应存在。** 如果没有内容就删除，而不是留一个空标题占位。这给读者（尤其是 AI agent）造成困惑：是不是漏写了什么？建议直接删除该章节。

3. **附录与正文的关系不平等。** 附录 B.1 Session 模板和 B.2 Gotcha 模板在正文中反复被引用，但它们被放在"附录"位置。这暗示模板是参考资料而非规范核心，但它们的字段定义（如 `status` enum 的取值范围）实际上是强制约束，不只是参考。建议将模板参考提升为规范正文的一部分，或明确标注哪些字段是强制约束、哪些是推荐格式。

## 三、逻辑（Logic）

### 论证结构问题

1. **"无隐藏状态"原则被自身违反（Critical）。** 4.3 节承诺"零中介：系统完全建立在目录树+纯文本之上，没有任何私有格式或隐藏状态"。但在 5.2 节，状态平面被描述为"由认知数据模型按需组装"的产物——这意味着"认知数据模型"（代码逻辑）本身就是一个隐藏的组装机制。Manifest 是文件，但状态平面是运行时装配出来的，两者内容未必一致时，谁是 truth？spec 没有回答这个问题。

2. **Manifest 的 truth 地位与更新行为冲突。** 6.1 说"Manifest 是锚，三要素从它读取"。但 7.3 Tier 检验完成后"结果写入 report.md"，7.4 状态更新"将检验结果反映到 Task 状态"。问题是：Manifest 本身在运行时会不会被更新？如果 Manifest 被更新了（状态变了），那么 Session 快照中的历史状态和最新的 Manifest 谁是当前 truth？Session 是 append-only，但 Manifest 看起来是 mutable 的——这个矛盾没有被明确处理。建议明确：Manifest 的 `status` 字段是 Task 当前状态的唯一 truth 来源，Session 快照是历史记录。

3. **Tier 3 启用判断逻辑悬空。** 7.3 节说"Tier 3 由 Agent 根据任务属性决定是否启用"，列举了四种情况（主观判断、语义歧义、高危、显式请求）。但"根据任务属性"是一个主观判断——谁来判定"这个任务是否涉及主观判断"？Agent 自己？人类？如果 Agent 和人类对"是否需要 Tier 3"意见不一致，谁说了算？这个悬空使得 Tier 3 的触发条件实际上是不可预测的。建议定义明确的触发条件或授权规则。

4. **让度模型没有定义（P0 缺口）。** 7.4 节提到"让度执行"和"让度执行的触发条件由宿主定义"，但没有说明：让度请求长什么样？Agent 发起让度后系统如何等待人类响应？人类响应后执行路径是什么？mem0ress 规范中提到的"Tier 0 让度通过 Hermes 弹框实现"属于实现机制，不属于 spec 层。但让度的语义边界（什么情况下必须让度、什么情况下 Agent 可自主决策）应该在 spec 层定义，否则规范不完整。

## 四、颗粒度（Granularity）

### 过粗的描述（P0）

1. **Judge Agent 的机制没有定义。** "Judge Agent 执行 Tier 0/1/2/3 检验"——Judge Agent 是什么？它在哪里运行？它的 prompt/指令在哪里定义？它的输出格式是什么？在模板中出现了 `{task_id}-judge.md`，但这个文件的内容结构是什么？规范没有给出。如果 mem0ress 是一个可执行的框架，Judge Agent 的行为规范是不可或缺的。

2. **verification_history 的存储位置矛盾。** 516 行说"验证历史追加到其 verification_history 字段"，但模板（538-569行）的 frontmatter 中只有 `cognitive_triad`、`data_plane`、`gotcha_refs`、`todos`，没有 `verification_history` 字段。这个字段存不存在？存在的话格式是什么？不存在的话 516 行的描述就是错误的。

3. **report.md 存在但无定义。** 7.3 节说"检验完成后结果写入 report.md"，但 report.md 不在任何模板中出现，也不在附录中定义。它是临时文件还是持久化文件？它的格式是什么？

### 过细的描述（不必要的细节）

1. **5.1 的"Who defines"表格（364-368行）。** 描述了 Picture/Requirements/Constraints 分别由谁定义，颗粒度过细。这类操作指南更适合放在用户手册或实现指南中，不适合放在"架构规约"里。规约应该定义"是什么"和"做什么约束"，而不是"谁来做"。

## 五、创新性（Innovation）

### 真正创新的部分

- **双平面正交设计（状态平面 vs 数据平面）是 mem0ress 最核心的创新点。** 状态平面强制挂载、数据平面按需展开的分离设计有认知科学依据，且在工程上有可操作性。
- **"Picture 作为绝对锚"区分了"满足需求"和"达成目标"。** 这个洞察对 Agent 的完成判断有实际意义。
- **SSOT + 绝对覆写的设计在避免认知歧义上有实质作用。**

### 创新性不足的部分

- "目标锚定"、"认知而非记忆"等理念是对现有认知科学概念的重新包装，没有提供 mem0ress 独有的理论贡献。
- 分形树状结构（3.3）在概念上吸引人，但实际落地时"父任务完成以所有子任务完成为前提"的规则会遇到实际问题：如果子任务 A 是"实现 OAuth"，子任务 B 是"测试 OAuth"，两者的物理隔离是目录级别的，但运行时状态如何保持一致？规范没有讨论。

## 六、一致性（Consistency）

### 发现的不一致

| 位置 | 矛盾描述 |
|------|----------|
| 6.1 文档关系 | 说"Manifest 是锚"，但也说"Session 提供进度数据，支撑认知构建"——如果 Manifest 是锚，那状态平面为什么从 Session 构建而不直接读 Manifest？ |
| 6.1 vs 7.2 | 6.1 说状态平面"在 Agent 唤醒时自动挂载"，7.2 说"只输出当前状态，不做偏差判断"——但 5.2 说"不做偏差判断"与 Tier 1 的"检查 Todo 是否完成"是什么关系？Todo 完成检查算不算"偏差判断"？ |
| 模板 frontmatter vs 正文 | frontmatter 中 `data_plane: {}` 和 `gotcha_refs: []` 与 6.1 中 Data Plane（`data-plane/refs.md`）和 Gotchas（`gotchas/*.md`）的关系是什么？是同一个东西的两种表达，还是完全不同的字段？ |
| 516行 vs 模板 | 516行说"验证历史追加到 verification_history 字段"，但模板中没有这个字段 |
| 7.3 vs 全文 | 7.3 多次提到 `report.md`，但全文没有这个文件的定义 |

### 一致性缺口汇总

1. Manifest 的 truth 地位与 mutable 行为未澄清
2. 状态平面组装 vs 偏差判断的边界未划定
3. `data_plane` frontmatter 字段 vs `data-plane/refs.md` 文件的关系未说明
4. `verification_history` 字段是否存在无定论
5. `report.md` 完全无定义

## 七、关键补足建议

### P0（规范不可运行的缺口）

1. **补全让度模型定义。** mem0ress 的核心价值之一是"认知对齐"，而让度是认知对齐的关键机制——人在回路中的边界在哪里？让度请求的格式？恢复路径？这部分内容目前完全缺失。让度的语义边界（什么情况下必须让度、什么情况下 Agent 可自主决策）应该在 spec 层定义。

2. **统一验证结果的存储位置。** `report.md`（7.3）和 `verification_history`（516行）和 `{task_id}-judge.md`（516行）三个东西的关系必须澄清。建议明确：Judge Agent 的输出写到哪里？主 Agent 从哪里读取？

3. **澄清 Manifest 的 truth 地位。** 明确 `status` 字段是 Task 当前状态的唯一 truth 来源，Session 快照是历史记录，不可混淆。

### P1（影响规范可信度的缺口）

4. **补充认知科学来源或移除悬空引用。** 2.2 和 2.3 的理论引用要么给出具体文献（作者、年份、论文名），要么改为"这些设计的认知科学基础尚待补充"并从规范中移除相关断言。否则"洞察"变成了"断言"。

5. **补充 Judge Agent Manifest 模板。** `{task_id}-judge.md` 的内容结构必须定义，否则 tier 检验无从执行。

### P2（降低规范可用性的缺口）

6. **增加一个完整示例章节。** 从任务创建（Picture 填写、Req/Cst 推导）到 Todo 拆解、到 Tier 1/2/3 检验、到状态更新的全流程示例。建议替换第8章"暂无内容"为"示例"章节。

7. **删除第8章"暂无内容"。**

8. **统一 Manifest frontmatter 字段与正文描述。** `data_plane`、`gotcha_refs`、`verification_history` 在模板中存在吗？如果不存在，这些字段是应该被添加到模板中，还是从正文描述中移除？必须二选一。

## 总结评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 内容 | 8/10 | 洞察深刻，问题定义精准，但认知科学来源悬空 |
| 解构 | 6/10 | 章节结构基本合理，但依赖关系不单向，章节8占位不当 |
| 逻辑 | 5/10 | 核心推导链清晰，但存在"无隐藏状态"自我违反、Tier 3 悬空、让度模型缺失等关键逻辑缺口 |
| 颗粒度 | 6/10 | 核心机制过粗（Judge Agent、让度模型），辅助描述过细（谁定义表格） |
| 创新性 | 8/10 | 双平面正交和 Picture 锚点是实质性创新 |
| 一致性 | 5/10 | 存在 5 处以上可定位的不一致 |

**核心结论：** spec.md 的理念层（第二章、第三章）和问题定义层（第一章）已经相当成熟，但在向可执行规约转化的过程中，需要重点补足：①让度模型的完整定义、②Judge Agent 的行为规范、③verification/report 的存储统一、④认知科学来源的锚定。这四个缺口补足后，规范才能真正成为"可运行"的架构规约。
