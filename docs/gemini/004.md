将 Picture 和 Requirements 提取到外部，构建一个“任务级 Harness（测试/评估台）”，这是一个极具工程敏锐度且非常成熟的架构设计。

你提到的这个概念非常契合目前前沿 Agent 设计中的 Supervisor（监督者） 或 Reflection Loop（反思回路） 模式。Agent 系统最大的通病就是“走神（Drift）”——在执行长流程任务时，容易沉迷于解决中间遇到的无限个小 bug，从而偏离了最终的画面。

把 Harness 独立出来，就相当于给执行任务的 Agent 配备了一个铁面无私的“质检员”。特别是你提出“从 todo 列表中获取子任务状态，而不是递归检查”，这是一个非常务实的工程折衷（Pragmatic Trade-off），能有效避免 AI 陷入无限递归和上下文爆炸。

对于这个任务级 Harness 的设计，我有以下几个维度的思考和建议：

1. Harness 的三级短路评估模型 (Short-Circuit Evaluation)
既然 Harness 包含了对 Todo、Requirements 和 Picture 的检查，这三者的验证成本（算力、时间、Token）是完全不同的。为了保证系统的轻量级，Harness 应该采用短路求值的逻辑，从下往上进行：

Tier 1: 机械状态检查 (Sub-task Todos) —— 成本：极低

动作： 解析 Markdown 文件中的 [ ] 状态。

逻辑： 如果 Todo 列表里还有没打勾的关键子任务，直接判定 Harness 未通过。系统不需要调用任何 LLM 进行后续检查，直接提示 Agent 继续执行未完成的 Todo。

Tier 2: 严格指标验证 (Requirements) —— 成本：中等

动作： 执行确定性的脚本、测试用例或正则匹配。

逻辑： 比如 Requirement 是“API 响应时间 < 200ms”或“代码通过 ESLint 检查”。这些是客观的、硬性的标准。如果有任何一条 Requirement 未满足，Harness 报错，并将具体的错误日志（Error Log）抛回给 Agent。

Tier 3: 自然语义理解 (Picture Validation) —— 成本：最高

动作： 调用高级 LLM 进行语义判定。

逻辑： 只有当 Tier 1 和 Tier 2 都通过时，才进入这一步。Harness 会把当前的任务产出（例如最终的代码、UI 截图的描述、测试总结）与外置的 Picture 进行对比。询问 LLM：“产出是否真正达成了这个画面？”

2. 触发机制的设计 (Trigger Points)
Harness 作为一个“外部环（Outer Loop）”，不能也不应该在 Agent 执行每一步时都去阻断。需要精心设计它的介入时机：

断点触发（Checkpoint Trigger）： 当 Agent 主动标记某个 Sub-task 完成时，触发一次轻量级的 Harness 检查（仅检查当前 Sub-task 相关的 Requirement）。

里程碑触发（Milestone Trigger）： 当所有的 Sub-task (Todo) 都被标记为 [x] 时，自动触发一次完整的 Tier 1 到 Tier 3 的 Harness 终检。

求助触发（Stuck Trigger）： 当 Agent 连续进行多次无效尝试（比如同一个 bug 修复了 3 次依然报错），强制挂起当前执行流，调用 Harness 重新比对 Picture，看看是不是思路完全走偏了。

3. Harness 与执行上下文的“物理隔离”
为了让 Harness 保持客观，它的上下文（Context）必须与执行任务的 Agent 物理隔离。

执行者 Agent： 满脑子都是“这里的变量为什么是 null”、“环境怎么又配不通了”、“刚才那个报错该怎么解”。它的上下文非常混乱且充满细节。

Harness 评判者： 它的上下文中只应该包含：任务的 Picture、Requirements、Todos 状态，以及执行者提交的最终产出状态（State）。

在架构上，Harness 更像是一个独立的函数调用：evaluate_harness(task_manifest, current_state)。它不关心你是怎么做的，只关心结果对不对。

4. 数据结构落地：将 Harness 融入纯文本架构
我们可以将 Harness 的概念无缝集成到我们之前讨论的纯文本 Markdown 结构中：

YAML


---
id: task_user_auth
type: task
status: in-progress

# === 任务级 Harness 外部配置 ===
harness:
  picture: "用户能够顺畅地使用邮箱注册、登录，并能够重置密码。UI 交互符合设计规范且没有卡顿。"
  requirements:
    - rule: "所有核心逻辑覆盖单元测试，覆盖率 > 80%"
      validator: "npm run test:coverage" # 可选：直接挂载可执行的验证脚本
    - rule: "响应延迟 < 200ms"
    - rule: "无 ESLint 报错"
---

# === Harness 检查项：Todo List (Tier 1) ===
## Sub-tasks
- [x] 开发注册 API
- [x] 开发登录 API
- [ ] 开发密码重置逻辑 (未完成，Harness Tier 1 阻断)

# === 执行区域 ===
## 进展日志
- 2026-05-01: 注册 API 已完成测试。
总结
你引入的外部任务级 Harness 是实现高度自治且不脱轨 Agent 的点睛之笔。

如果说 mem0ress 的 Plane 和 Tag 系统解决了“我是谁，我在哪，我有哪些信息”的问题，那么这个独立的 Harness 就解决了“我做完了吗？我做的对吗？”的问题。它通过明确的、分层的（Todo -> 严格指标 -> 语义画面）边界约束，能够让你的 Agent 系统具备极高的工程鲁棒性。
