>> 这份文档不仅是对我们讨论的总结，更是一份可以直接作为 mem0ress 核心开发蓝图（Architecture Specification）的规范说明。我们将系统正式定义为“任务认知与态势感知系统（Task Cognition & Situational Awareness System）”。

# mem0ress: 认知态势感知系统架构规约

## 1. 核心哲学 (Core Philosophy)

mem0ress 摒弃了传统的“被动记忆存储”理念，转而构建基于 AI Agent 的心智模型（Mental Model）。

* 不存流水账，只存状态突变 (**Cognitive Delta**)。
* 物理隔离知识库 (**Dual-Track**)： Agent 是 CPU，mem0ress 是内存 (RAM)，外部知识库 (Vector DB) 是硬盘。内存不直连硬盘，一切知识必须经由 Agent 蒸馏后注入内存。
* 目标锚定 (**Goal-Anchored**)： 所有的信息必须服务于当前活跃的任务 (Task)，没有悬空的数据孤岛。

## 2. 目录拓扑 (Directory Topology)

保持极简的扁平化文件系统，杜绝深层嵌套，便于大模型和外部脚本直接挂载和遍历。

```Plaintext
.mem0ress/
├── tasks/            # 意图锚点：所有的任务节点 (仅存 Root Task)
├── info/             # 认知增量：所有的决策、报错、蒸馏知识
├── inbox.md          # 灵感中转站：未格式化的游离想法与待确认 Bug
└── .plane.yaml       # 瞬态工作台：AI 会话期间动态生成的全局态势感知 (不持久化)
```

## 3. 数据模型定义 (Data Schemas)

系统完全基于`Markdown + YAML Frontmatter`构建。

### 3.1 Task (意图锚点与 Harness)
位于`tasks/task_<id>.md`。Task 是 Agent 存在的目的。禁止为子任务创建独立文件，子任务仅作为当前文件内的 Todo 列表存在。

````markdown
---
id: task_user_auth
type: task
status: in-progress      # created | in-progress | completed | abandoned
tags: [auth, security, oauth]

# === 任务级 Harness (质检器) 外部配置 ===
harness:
  picture: "用户能够顺畅地使用邮箱注册、登录，并能够重置密码。交互无卡顿，无安全漏洞。"
  requirements:
    - rule: "所有核心逻辑覆盖单元测试，覆盖率 > 80%"
      validator: "npm run test:coverage" # 可选的外部触发脚本
    - rule: "响应延迟 < 200ms"
    - rule: "无 ESLint 报错"
---
# 实现用户鉴权模块

## Sub-tasks (Harness Tier 1 检查点)
- [x] 开发注册 API
- [x] 开发登录 API
- [ ] 编写 Auth 中间件

## 进展日志 (Activity Log)
- 2026-05-01: 登录 API 已打通，准备处理 JWT 签发逻辑。
````

### 3.2 Info (认知增量与决策)
位于 info/info_<id>.md。所有脱离当前 Task 即失效的信息。通过 tags 与 Task 产生多维软链接。

````markdown
---
id: info_jwt_decision
type: info
tags: [auth, security, jwt]
lifecycle: hot           # hot | cold (由后台脚本管控，禁止 AI 消耗 token 去管理)
weight: decision         # default | decision | failure_patch 
timestamp: "2026-05-01T10:15:00Z"
---
# 放弃 Redis Session，改用 JWT

**背景:** 
原计划使用 Redis 存储 Session，但在跨域微服务调用时存在状态同步延迟。

**决策 (Decision):**
全面改用无状态的 JWT token，并在 Gateway 层进行验签。
*注意：这是一个 [decision] 级 Info，只要 `auth` 标签活跃，本决策强制常驻内存，不可违背。*
````

### 3.3 Plane (全局态势感知视窗)
位于 .plane.yaml。这是 Agent 的前额叶皮层，每次 Session 唤醒时瞬间生成，代表当前的上下文聚焦点。包含对“未知”的感知。

```yaml
session_start: "2026-05-01T10:00:00Z"
current_focus: 
  task_id: task_user_auth
  picture_alignment: "50%"  # 当前距离画面达成的预估
hot_info_context:
  - id: info_jwt_decision
    match_tags: [auth, security]
    type: decision
# 认知盲区：当 Agent 发现 Plane 无法支撑执行时，主动写入盲区，触发对 KB 的检索
cognitive_gaps:
  - "Node.js 环境下最优的 JWT 非对称加密实现方案是什么？"
```

## 4. 核心系统机制 (Core Mechanisms)

### 4.1 知识蒸馏与双轨隔离 (Knowledge Distillation)

 1. 触发: Agent 发现 .plane.yaml 中存在 cognitive_gaps。
 2. 检索: Agent 调用外部工具 (Tool: search_kb) 访问向量数据库或全网文档。
 3. 蒸馏: Agent 在沙盒上下文中阅读长文档。
 4. 内化: Agent 提取核心结论，创建一条 type: info 写入 mem0ress/info/ 目录。坚决禁止将长篇原始文档直接写入 mem0ress。

### 4.2 任务级 Harness (三级短路评估台)

当 Agent 在 task.md 中勾选了某个子任务 (- [x]) 或所有子任务完成时，触发独立的 Harness 质检流：

  * Tier 1 (机械状态): 扫描 .md 文件，若有 - [ ] 未完成，直接阻断，提示 Agent 继续。
  * Tier 2 (严格指标): 检查 requirements。若带有 validator，则执行外部脚本。失败则阻断。
  * Tier 3 (语义画面): 唤醒高级 LLM 独立评估上下文。将当前代码/产出与 picture 对比。“虽然单元测试过了，但用户体验顺畅吗？”
  * 失败反馈环 (Failure Patch): 若 Harness 阻断，系统不只是抛出 Error，而是自动生成一条 weight: failure_patch 的热点 Info 强制注入 Plane，告知 Agent 偏离了哪里。

### 4.3 外部冷热生命周期 (Cron-driven GC)

Agent 不负责垃圾回收。由系统底层的 Python/Node 脚本（例如 Cron Job）定期执行：

 1. 扫描所有 status: completed 的 Task。
 2. 提取该 Task 独占关联的 Info 文件。
 3. 将其 Frontmatter 强制修改为 lifecycle: cold。
 4. （可选）若某 Info 的 updated_at 超过 7 天且从未在最近的 Plane 中被引用，降温为 cold。

### 4.4 Inbox 中转机制

避免打破当前心智模型。当执行 Task A 时发现 组件 B 的潜在 Bug：

  * Agent 不立刻去创建 Task B。
  * Agent 将问题无格式地 append 到 inbox.md 底部。
  * 在会话结束或开始时，Agent 询问用户：“Inbox 中有 3 个遗留想法，是否需要转化为正式 Task ？”
  
---

## 架构总结
mem0ress 通过纯文本的透明度，确保了系统的可观测性；通过 Harness 和 Picture，确保了执行不脱轨；通过双轨隔离，保持了认知高信噪比。这是一个专为高级自主 Agent 设计的“认知操作系统内核”。
