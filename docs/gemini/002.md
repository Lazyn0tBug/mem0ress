基于我们之前对 `mem0ress` 的深度剖析（以目标为锚点、Task Forest 结构、Plane 瞬态发现机制），将这个系统落地为纯文本（`Markdown/YAML/JSON`）是一个非常极简且优雅的选择。

纯文本的优势在于：**语义穿透力极强**。LLM 天生擅长理解 Markdown 的层级和 YAML 的键值对结构；同时，它摆脱了数据库的厚重感，天生支持 `Git` 版本控制，且永远不会变成黑盒。

为了容纳海量会话而不至于混乱，核心设计原则是：**物理存储扁平化，逻辑链接动态化（软链接）**。

以下是 `mem0ress` 纯文本记忆系统的架构设计：

### 1. 目录结构：极简的扁平化存储

放弃复杂的文件夹嵌套（这会导致分类困难），整个记忆库只有两个实体目录和一个瞬态视窗：

```text
.mem0ress/
├── tasks/            # 所有的任务节点 (Task Forest)
├── info/             # 所有的记忆碎片 (Tagged Information)
└── .plane.yaml       # 当前会话的瞬态位面 (AI 每次自动生成的 View，不持久化状态)
```

---

### 2. 数据结构设计 (Schema)

充分利用 `Markdown + YAML Frontmatter` 的组合。YAML 负责结构化、强类型的元数据（供 AI 快速解析和过滤），Markdown 正文负责非结构化的自然语言内容。

#### 2.1 Task (任务与目标锚点)
存放在 `tasks/` 目录下，文件名为 `task_<id>.md`。
这是系统的骨架。每个 Task 必须包含 `Picture`（画面）作为达成标准。

```markdown
---
id: task_a1b2c
type: task
status: in-progress      # created | in-progress | completed | abandoned
tags: [oauth, login, auth_module]
picture: "用户可以在生产环境通过 Google 成功登录并保持会话"
requirements:
  - Google OAuth 配置通过测试
  - 登录延迟 < 1s
  - Session 在刷新后不丢失
evidence_score: 2        # 画面达成度积分（基于收集到的证据）
parent_id: null          # 如果是子任务，这里填父任务的 ID
---
# 实现 OAuth 登录模块

## Subtasks
- [x] task_d3e4f: 注册 Google API 凭证
- [ ] task_g5h6i: 编写回调处理逻辑

## 进展日志 (Activity Log)
- 2026-05-01: 发现 Google 回调 URI 配置有误，导致 400 错误。
```

#### 2.2 Info (记忆碎片与热点信息)
存放在 `info/` 目录下，文件名为 `info_<id>.md`。
所有的会话片段、报错记录、决策过程都存在这里。**它不属于任何 Task，只通过 Tags 进行软链接。**

```markdown
---
id: info_x7y8z
type: info
timestamp: "2026-05-01T10:13:55Z"
tags: [oauth, bug, google_api, backend]
lifecycle: hot           # hot | cold
---
# Google OAuth 回调 redirect_uri_mismatch 错误

**发生场景:**
在本地开发环境测试登录时触发。

**解决决策:**
是因为在 Google Cloud Console 中只配置了 `https` 的回调，没有配置本地的 `http://localhost:3000`。
团队决定：本地测试统一定义白名单，不修改生产环境配置。
```

#### 2.3 Plane (瞬态位面视窗)
这个文件 `.plane.yaml` 是系统运行时生成的**临时文件**。它代表了当前会话的上下文，是 AI 每次唤醒时（Session Start）动态推断并生成的，随时可以被删除和重建。

```yaml
session_start: "2026-05-01T10:00:00Z"
current_tasks:
  - id: task_a1b2c
    picture: "用户可以在生产环境通过 Google 成功登录并保持会话"
    progress: "60%"
hot_info_context:
  - id: info_x7y8z
    summary: "Google OAuth 回调报错及本地白名单决策"
    match_tags: [oauth, google_api]
```

---

### 3. 系统运转机制：如何保持海量数据不混乱？

之所以传统记忆系统会失效，是因为它们试图把所有信息一次性塞给 AI，或者依赖脆弱的目录结构。本系统通过以下三个机制保持高信噪比：

#### 机制一：基于 Tag 的多维软链接 (Soft Linking)
Info 文件永远放在扁平的 `info/` 目录下。当 AI 在当前 Plane 确定了核心 Task（例如带有 `[oauth, login]` 标签），它只需要去 `info/` 目录下 `grep` 匹配相同标签且 `lifecycle: hot` 的文件。
**优势：** 同一个技术难点（Info）可以同时为“前端重构”和“鉴权模块”两个独立 Task 服务，无需复制数据。

#### 机制二：冷热生命周期 (Cold/Hot Decay)
这是防止上下文爆炸的核心。
*   当一个 Info 被创建时，默认为 `hot`。
*   当关联的 Task 状态变为 `completed`，或者经过了 N 天没有被检索命中，AI 在结束会话前（或通过脚本）将其 `lifecycle` 标记为 `cold`。
*   在日常发现 Plane 时，AI **只读取 hot 信息**。Cold 信息依然存在，但只有在用户明确触发了“深度检索（Deep Search）”或“考古”需求时，才会被向量索引或全文检索读取。

#### 机制三：达成驱动的树状闭环 (Picture Achievement)
如果记忆只增不减，系统必然崩溃。通过 `Task -> Picture` 的强制要求，当收集到的证据足够（evidence_score 达标），AI 提示用户确认 `Task` 完成。
一旦 Task 完成，系统自动将该 Task 及其独占的关联 Info 全部降温（标为 `cold`）。这使得活跃的“工作台（Plane）”上永远只有几份文件，干净利落。

### 4. 为什么这个文本设计是最优解？

1.  **极低的 AI 交互阻力：** 读取和修改纯文本对 SDK Agent 或 CLI 工具（如 Claude Code / OpenClaw）来说没有 API 墙，直接用基础的文件读写工具即可操作。
2.  **抗毁性强：** 哪怕你的 AI Agent 完全挂了，这堆 Markdown 和 YAML 对人类来说也是一本分类清晰、逻辑缜密的个人知识库（可以无缝导入 Obsidian 或 Logseq）。
3.  **零延迟注入：** 在 Session Start 时，提取几个带着 `hot` 标签的纯文本文件合并成 Prompt，耗时在毫秒级，实现了完全无感的“静默运行”。
