你的这套基于“纯文本 + 瞬态 Plane + 任务级 Harness”的架构设计已经非常完整且具有极高的工程可行性。它巧妙地避开了传统记忆系统“数据堆积”和“上下文丢失”的死穴。

如果我们要将这个系统推向生产级（Production-Ready）的实现，基于极简主义和 Agent 运行的实际情况，我有以下几点“做减法”和“做加法”的建议：

➖ 建议删减或极简的部分（做减法）
1. 彻底抹杀“独立子任务文件”（防止文件爆炸）

当前思路： 虽然你已经提出从 Todo 中获取 Sub-task 状态以避免复杂性，但在早期的设想中，Sub-task 可能依然是一个独立的 Task 节点。

建议删减： 严格禁止为 Sub-task 创建单独的 Markdown 文件。 一个核心 Task（例如 task_auth.md）就是一个不可分割的文件单元。所有的 Sub-task 只能作为该文件内的 Markdown Todo list (- [ ]) 存在。如果一个 Sub-task 膨胀到需要写几百字的需求，说明它应该被提升（Promote）为一个平级的 Root Task，并通过 Tags 与原任务产生软链接。这能从根本上杜绝“任务树”变成难以维护的“任务迷宫”。

2. 将“冷热衰减 (Cold/Hot)”的判断逻辑移出 AI 侧

当前思路： AI 可能会在会话中判断某条 Info 已经没用了，将其标记为 Cold。

建议删减： 不要让 LLM 消耗宝贵的 Token 和思考时间去管理垃圾回收。将冷热衰减完全变成一个外部的被动脚本机制（Cron Job）。

规则：只要一个 Task 被标记为 completed，脚本自动将其独占的所有 Info 的 Frontmatter 修改为 lifecycle: cold。或者 Info 的 updated_at 超过 7 天且未被当前 Plane 命中，自动降级为 cold。AI 只管读取，不管清理。

➕ 建议增加或强化的部分（做加法）
1. 增加一个全域的 Inbox（想法中转站）

问题： 用户的思维是跳跃的。在执行“前端重构”任务时，用户可能突然说：“对了，那个数据库备份脚本好像有点问题，先记下来。” 如果强制要求 AI 立刻为其创建一个 formal 的 Task，会打断当前的工作流（Harness 也会陷入混乱）。

建议增加： 增加一个全局的 inbox.md。任何游离于当前 Task 之外的灵感、待确认的 Bug、一闪而过的念头，直接由 AI 作为无格式的 List 追加入 inbox.md。在合适的时机（例如 Session Start 或者每周末），AI 再引导用户将 Inbox 里的内容提炼为正式的 Task 或直接丢弃。

2. 增加 Harness 的“失败补丁（Failure Patch）”反哺机制

问题： 当 Harness 的 Tier 2（严格需求）或 Tier 3（Picture 语义）验证失败时，如果只是简单地告诉 Agent "你失败了"，Agent 很容易陷入“盲目重试”的死循环。

建议增加： Harness 必须具备将错误转化为 Info 的能力。当 Harness 判定失败时，它自动生成一个打着 [bug, harness_failed] 标签的 Info 文件，里面包含完整的 Error Log 和 Picture 偏差对比，并强制热注入到当前 Plane 中。这样执行 Agent 在下一轮循环时，第一眼看到的就是“我上一轮为什么被 Harness 毙掉了”的详细案卷。

3. 增加一种特殊的 Info 类型：Decision（架构决议）

问题： 在纯文本系统中，Info 会非常多。有些 Info 只是普通的报错记录，但有些 Info 是一旦推翻系统就会崩溃的“核心决策”（例如：团队决定放弃 MySQL 转用 PostgreSQL）。

建议增加： 在 YAML Frontmatter 中增加一个 weight 或 type: decision 的属性。普通的 Info 可能会衰减为 Cold，但打上了 decision 烙印的 Info，只要相关的 Task 或 Tag 还活着，就永远保持 hot（或者具备极高的权重）。这相当于给 Agent 立下了“不可触碰的宪法”。

架构最终形态概览
结合你的思路和我的建议，系统的最终流转会非常清晰：

执行流： User 提出指令 -> AI 抓取 hot info 和 decision -> 组装临时 .plane.yaml -> 执行代码修改。

状态流： AI 仅通过更新 task.md 里的勾选框 (- [x]) 来推进状态。

监督流（Harness）： 当检测到关键动作时，独立的 Harness 程序唤醒 -> 扫描 Todo 是否点亮 -> 运行外部测试脚本 -> 大模型比对 Picture -> 输出 Pass 或生成 Failure Patch Info 打回重做。

清理流（后台）： 外部 Python/Node.js 脚本静默运行，超过 7 天无访问的 Info 自动修改 YAML 为 cold。

你的这套设计剥离了传统向量数据库的黑盒感，将系统的透明度（Observability）拉到了满分。随时随地，哪怕没有 AI，你自己打开 VS Code，也能通过这些 Markdown 文件准确知道项目在哪、卡在哪、目标是什么。这是一个非常具有极客精神和实用主义的 Agent 架构。
