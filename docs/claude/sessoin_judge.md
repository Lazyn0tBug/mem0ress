一、理论基础：为什么 LLM 可以做语义裁判
1.1 问题的本质
Tier 3 要解决的问题是：自然语言描述的成功状态，能否被机器判断为已达成？

这个问题在形式上属于**自然语言推断（Natural Language Inference，NLI）**的变体——给定一个前提（实际产出），判断它是否蕴含结论（Picture 所描述的成功状态）。经典 NLI 处理的是句子级别的蕴含，Picture 判断处理的是任务级别的语义对齐，粒度更大，但结构相同。

传统方法无法解决这个问题，原因是确定的：规则匹配无法理解"用户感知不到登录的存在"这句话的含义；BLEU/ROUGE 这类相似度指标无法判断两个表达完全不同的文本是否在说同一件事；结构化测试能验证"OAuth 流程存在"，但无法验证"体验是无感知的"。

LLM 可以做这件事，核心原因是：预训练过程中积累的世界知识和语义理解能力，使它能够推理"某种状态下用户会有什么体验"，而不只是匹配字符串。

1.2 实证支持
Zheng et al. 2023 的 MT-Bench 研究系统性地验证了 LLM-as-Judge 的可行性。核心发现：GPT-4 作为裁判与人类专家评分的一致性达到 80%+ ，超过了人类评估者之间的互评一致性（约 81%）。这说明在评估质量这件事上，强 LLM 已经接近人类专家水平。

但这个结论有一个重要限制：一致性高不等于准确率高。LLM 裁判与人类一致，不代表两者都是对的——它们可能系统性地共享同一个偏见。这一点在 Picture 判断中尤其需要警惕。

1.3 LLM 做裁判的认知机制
LLM 之所以能做裁判，依赖三种能力的组合：

语义组合理解：能理解"无感知"不是一个技术指标，而是对用户认知负荷的描述，并能将它映射到"无密码输入框、跳转流畅、无确认弹窗"这些具体表征。

反事实推理：能回答"如果 p99=487ms，用户会感知到停顿吗"这类问题，即使 Picture 里没有提到响应时间。

意图推断：能从"员工打开工作台"这个场景背景，推断出"员工不是技术用户"，进而对"友好错误信息"有更严格的语义理解。

这三种能力组合起来，才能判断一个技术实现是否真正达成了一个用自然语言描述的目标。

二、Picture 判断的特殊困难
2.1 Picture 是什么类型的陈述
Picture 是利益相关者视角的成功状态描述，这意味着它有两个特性：

第一，它描述的是体验，不是实现。"用户无需输入密码"描述的是用户的体验路径，不是 OAuth 技术规范。同样的体验可以由很多种技术实现达成，也可以由看起来技术正确的实现破坏（例如 OAuth 流程正确，但因为 session 没有持久化，用户每次打开页面都要重新授权）。

第二，它描述的是终态，不是过程。"员工直接进入工作台主界面"是一个状态，不是一系列步骤。判断这个状态是否达成，需要推断整个流程执行后用户所处的位置，不能只看局部。

2.2 证据问题：Judge 看到的不是现实
这是当前设计最薄弱的地方，需要直接承认。

Judge Agent 在 Tier 3 读取的是：

session.md 里主 Agent 写的 Code Progress（自然语言描述）
Data Plane 里的 commit ID + 文件路径
它读到的不是代码的实际运行行为，而是主 Agent 对代码行为的描述。

这产生了一个结构性问题：主 Agent 可能诚实但不准确（它认为实现正确，但实际有 bug）；主 Agent 可能准确但不完整（它描述了正确的部分，省略了有问题的部分）。Judge Agent 无法区分这两种情况，因为它只读到了描述。

这不是可以完全消除的问题，是协议设计的一个固有局限。但可以通过以下方式减轻：让 Judge Agent 读实际的测试输出（来自 Tier 2 的命令执行结果），而不只是 Code Progress 描述；让主 Agent 在 Code Progress 里写"这个测试通过了 / 失败了"，而不是"我实现了这个功能"。

2.3 评估边界问题
Picture 里存在一类描述，是 LLM 裁判无法可靠判断的：需要外部感知的主观体验。

"流畅"、"快"、"用户感知不到停顿"——这些描述依赖真实用户在真实环境中的感知，LLM 只能基于它对"什么情况下人会感知到停顿"的统计知识做推断，不能感知。

当 Picture 包含这类描述时，Tier 3 的可信度是有限的。这不是理由不做，而是应该在 judge.md 里如实标注：Judge Agent 的判断是基于语言推断的近似，不是基于真实用户测试的事实。

三、Prompt 工程：怎么问才能得到可信的判断
这是实施细节里最核心的部分。一个糟糕的 prompt 会让 Judge LLM 表现得像一个过于宽容的面试官，对什么都说"差不多达到了"。

3.1 基础结构：角色分离
你是 mem0ress 协议的 Judge Agent，执行 Tier 3 语义对齐检查。

你的职责边界：
- 只报告实际产出与目标图景之间的语义偏差事实
- 不给出修复建议
- 不推断主 Agent 的意图
- 不因为"大体上差不多"就判 PASS

你的输入是：
- 目标图景（Picture）：利益相关者眼中的终态，写给非技术人员看的
- 实际产出证据：来自测试命令输出和代码进展描述

你的输出只有两种：
- PASS：实际产出在语义上完整达成了图景，无遗漏维度
- FAIL：<具体偏差>，说明哪个维度未达成，为什么
3.2 Picture 维度分解（关键技术）
直接让 LLM 判断整个 Picture 是否达成，容易产生整体印象替代细节判断的问题——它会因为"大部分都对"而忽略一个关键的未达成维度。

正确做法是让 Judge Agent 先分解 Picture，再逐维度判断，最后汇总。这是 Chain-of-Thought 在评估任务上的应用。

第一步：请将以下 Picture 分解为独立的、可判断的语义维度。
每个维度描述一个利益相关者可感知的成功要素。

【Picture】
员工打开工作台时，无需输入任何密码，点击「使用企业账号登录」后
通过 Google 或 GitHub 账号完成授权，直接进入工作台主界面。
整个过程感知不到"登录"这个动作的存在，只感知到"进入了"。

第二步：对每个维度，基于实际产出证据判断是否达成。

第三步：若所有维度均达成，输出 PASS。
若任何维度未达成，输出 FAIL：[具体偏差]。
对上面这个 Picture，Judge Agent 应该能分解出：

维度 A：无密码输入（无密码输入框出现在流程中）
维度 B：支持 Google 和 GitHub 两个选项（非单一 provider）
维度 C：授权完成后直接进入主界面（无中间确认页、无二次跳转）
维度 D：登录过程的认知负荷极低（体验上"感觉不到在登录"）
维度 D 是 Tier 0/1/2 完全无法覆盖的，这正是 Tier 3 存在的意义。

3.3 证据锚定（对抗幻觉的核心手段）
Judge Agent 最大的失效模式是无证据幻觉：在没有足够证据时，基于对"正确实现应该是什么样"的先验知识，推断出 PASS。这是一种语义层面的 long-run 问题——看起来做了判断，实际上只是在重复训练数据里见过的标准答案。

对抗手段是强制证据锚定：

【判断规则】
你的每一个维度判断，必须引用实际产出证据中的具体内容作为依据。
如果某个维度在提供的证据中找不到支撑，判断结论为"证据不足，无法确认"，
不允许基于推断给出 PASS。

"证据不足，无法确认"视为 FAIL。
这个规则有一个重要推论：如果主 Agent 的 Code Progress 描述太模糊，Judge Agent 会返回 FAIL。这实际上是一种反向约束——倒逼主 Agent 在 session.md 里写有信息量的内容，而不是"实现了 OAuth 功能"这种空洞描述。

3.4 反驳测试（Adversarial Probing）
对于高置信 PASS 的维度，加入一个反驳步骤：

【反驳测试】
对于你判断为 PASS 的每个维度，请设想一个该维度实际未达成的场景，
并检查现有证据是否能排除这个场景。

例如：
- 维度 A 判断 PASS（无密码输入）
- 反驳场景：OAuth 授权后，系统要求用户"设置本地密码"
- 检查：Code Progress 中是否有证据表明这个场景不存在？

如果无法通过现有证据排除反驳场景，降低该维度的置信度或降级为 FAIL。
这个步骤会显著提高 Judge 的可靠性，代价是增加一次 LLM 调用或更长的 CoT 链。

四、失效模式与对策
4.1 位置偏见（Positional Bias）
LLM 对 prompt 中信息的权重不均匀——靠近开头和结尾的内容权重更高，中间的内容容易被降权。当 Picture 很长，或实际产出证据很长时，Judge 可能只对开头的维度做了认真判断，后面的维度被草率处理。

对策： 把 Picture 维度分解后，每个维度独立放在一个问题里，而不是一次性判断全部。对于有 N 个维度的 Picture，发 N 个独立判断请求（或者在一个请求里用明确的编号结构强制逐一回答）。

4.2 宽容偏见（Leniency Bias）
LLM 天然倾向于给正面反馈，在评估场景下表现为"差不多达到了"式的 PASS。这是训练数据和 RLHF 造成的系统性偏差，在 mem0ress 的场景下特别危险，因为 Judge 的 PASS 会直接触发任务完成。

对策一： Prompt 里显式声明"宁可 False Negative 也不接受 False Positive"：

本次检验是任务完成的最终把关。
False Positive（把未达成判断为达成）的代价远高于 False Negative（把已达成判断为未达成）。
当你对某个维度有疑虑时，输出 FAIL，不输出 PASS。
对策二： 多次调用取最严格结论。对同一个 Picture 发两次独立的判断请求（不同 temperature），如果其中任何一次返回 FAIL，最终结论为 FAIL。

4.3 自我一致性偏见（Self-Consistency Bias）
如果 Judge Agent 和主 Agent 使用同一个底层模型（例如都是 Claude），Judge 在评估主 Agent 描述的产出时，可能因为"这个描述方式和我自己写的一样"而产生过度信任。

对策： Judge Agent 的 prompt 里加入明确的怀疑指令：

实际产出的描述由另一个 Agent 撰写。你不应该假设这个描述是完整的或准确的。
你的判断依据是描述中明确包含的信息，不是对描述者能力的信任。
4.4 Picture 过于宏大导致的判断漂移
如果 Picture 写成了一段愿景宣言（"用户体验革命性提升"），Judge 无法对其做出有意义的判断——它要么输出无意义的 PASS（"是的，感觉上达成了"），要么输出无意义的 FAIL（"无法验证"）。

这不是 Judge Agent 的问题，是 Picture 的质量问题。 对策在任务创建阶段：Picture 必须描述可感知的终态，不允许写抽象价值主张。

在 Tier 3 执行前增加一个 Picture 可判断性检查：

在执行语义对齐判断之前，请评估 Picture 是否可判断：
- Picture 描述了利益相关者可直接感知的状态 → 可判断，继续执行
- Picture 描述了抽象的价值或方向 → 不可判断，输出 INCONCLUSIVE

INCONCLUSIVE 视同 FAIL，主 Agent 需要重新定义 Picture 后再触发检验。
五、在协议层面的增强建议
基于以上分析，当前 judge.md 的 Tier 3 设计应该补充以下内容：

一、Picture 维度分解结果应当写入 judge.md。 不只是最终 PASS/FAIL，而是每个维度的判断及其证据引用。这样主 Agent 读到 FAIL 时，能直接知道是哪个维度出了问题，而不是重新猜测。

二、证据不足应作为独立结论类型。 当前模板只有 PASS / FAIL，建议增加 INCONCLUSIVE: <缺失的证据>，表示"不是产出有问题，而是 Judge 无法判断"。这两种失败的处理方式不同：FAIL 需要修复产出，INCONCLUSIVE 需要主 Agent 补充证据（在 session.md 里写更详细的 Code Progress，或提供测试日志）。

三、Tier 3 的触发应附带 tier3_context。 当前协议里主 Agent 只传 tier3_requested: true，Judge 不知道为什么被请求做语义检验。应该允许主 Agent 传递触发原因，例如："Picture 中'无感知'的体验描述需要语义裁定，Tier 2 无法覆盖"。这个上下文能帮助 Judge 知道应该重点检验哪个维度。

六、一句话总结
Tier 3 的本质是把**"合同验收"**这件事自动化——在没有真实用户参与的情况下，用语言推理能力判断技术实现是否兑现了最初的承诺。它不是银弹，有证据依赖、宽容偏见、体验无法感知等固有局限，但在上述 prompt 工程和多重约束下，它能可靠地捕获那些 Tier 0/1/2 系统性无法发现的语义偏差——"Todo 都勾了，Requirements 都过了，但实际体验就是不对"这类问题，正是 Tier 3 存在的唯一理由。
