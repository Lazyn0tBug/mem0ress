# mem0ress FAQ — 设计哲学篇

本文档收录 mem0ress 核心设计决策背后的哲学思考。每个条目都试图回答"为什么这样设计"，而非"怎么工作的"。关于用法和命令，请参考 [tutorial.md](tutorial.md)。

---

## Q1: 为什么我们需要的是"认知"而不是"记忆"？

**A**: 记忆是向后看（Retrospective）的存储行为——回答"我们之前讨论了什么"。CAP 不是检索过去对话的存储系统，而是**前向的认知系统**——持续维持 AI 对当前目标、进度和认知缺口的感知。

两者的根本区别：

| 维度 | 记忆系统 | 认知系统 |
|------|---------|---------|
| 方向 | 向后看 | 向前看 |
| 触发 | 被动检索 | 主动感知 |
| 回答的问题 | "之前说了什么？" | "我要达成什么？我离目标还有多远？" |
| 与目标的关系 | 无关 | 强关联 |

**认知框架让 AI 始终知道自己在哪、要到哪、还差什么——而这正是长程任务中 Agent 最稀缺的能力。**

## Q2: 认知来自哪里？它是"记忆"检索出来的吗？

**A**: 认知来自**会话流中实时构建的信息平面**，而不是从存储中检索出来的历史记录。

传统的记忆检索逻辑是：**存储 → 提取**。Agent 需要什么，就从记忆存储中调取。

CAP 的认知构建逻辑是：**会话钩子（Session Hook）→ 当前轮次的切片 → 状态平面组装 → 认知投影**。认知不是被提取的，而是被**实时构建**的——它在每一轮 Agent 唤醒时重新生成，指向当前目标。

这意味着：
- 认知不存储"过去发生了什么"
- 认知记录的是"当前目标下，什么信息是有意义的"
- 过时的、与当前目标无关的信息不会被投影到认知平面

**认知是前向的、目标驱动的、信息过滤后的语义切片——不是历史记录的回放。**

## Q3: 为什么一切皆任务？

**A**: CAP 的一切皆任务（Everything is a Task）遵循两个设计哲学：**冲突避免优于协调**，以及**认知单元的同构性**。

### 冲突避免

协调机制的本质是在冲突发生后解决它。但更好的设计是通过物理隔离让冲突根本不发生。CAP 通过目录深度表达任务依赖关系，不同任务物理隔离，父任务必须等待所有子任务完成才能完成——这使冲突无从产生。

### 同构性

所有认知单元（Task）拥有相同结构：Picture + Requirements + Constraints + Todos + Session + Gotchas + Judge。这带来：
- **可验证性**：每个 Task 都有明确的完成标准
- **可分解性**：复杂目标自然拆解为层次化子任务
- **无歧义解析**：Agent 不需要为不同任务类型编写不同的理解逻辑

**当所有认知单元都遵循同一协议时，认知处理的复杂度降到最低。**

## Q4: 为什么 CAP 不需要冲突协调机制？

**A**: CAP 的设计哲学是**冲突避免优于冲突协调**。

协调机制隐含一个前提：冲突是不可避免的，我们需要工具来处理它。CAP 认为这个前提本身就是错误的设计信号。

CAP 通过三层设计消除冲突：

1. **物理隔离**：不同任务处于不同目录，冲突无从发生
2. **依赖强制**：父任务目录下嵌套子任务，通过目录深度表达依赖关系
3. **继续拆分原则**：当两个任务出现边界冲突时，正确的处理方式是继续拆分任务直到冲突消除——而非引入协调机制

冲突出现时，不是记录下来等待解决，而是追溯到任务定义层面，重新划分边界直到冲突消除。如果确实无法继续拆分，则让度给人确认。

**如果两个任务真的冲突，那说明它们本来就不应该是两个独立的任务。**

## Q5: 为什么 Picture 是完成标准，而不是 Requirements、Constraints 或子任务清单？

**A**: 因为 Picture 回答的是**语义成功状态**，而其他三者回答的是**达成路径**。

| 要素 | 回答的问题 | 本质 |
|------|-----------|------|
| **Picture** | "完成后，世界是什么样的？" | 语义目标 |
| **Requirements** | "有哪些指标可以验证？" | 可验证条件 |
| **Constraints** | "什么绝对不能发生？" | 不可逾越的底线 |
| **子任务清单** | "要到达目的地，走哪条路？" | 执行路径 |

一个经典的失败模式：Agent 完成了所有 Requirements、所有子任务、所有 Constraints 的检查——但 Picture 未达成。例如，Agent 完成了一份白皮书的所有章节，但用户说"这不是我想要的"。

Picture 作为完成标准防止这种"勾选心态"：即使所有条目完成，如果 Picture 未达成，任务就不算完成。它要求 Agent 始终瞄准确语义目标，而非机械地执行清单。

**子任务和 Requirements 是路径，Picture 是目的地——只盯着路径的人永远不知道是否到达了目的地。**

## Q6: 什么是"Data Soup"困境？CAP 如何避免？

**A**: Data Soup 发生在记忆系统将所有信息存入无结构的池子时——信息失去边界、新旧混杂、无法区分当前与过时，导致上下文污染和熵增。

CAP 通过三层机制避免 Data Soup：

1. **目标锚定**：信息仅在与活跃 Task 关联时才有意义。失去目标指向的信息视为噪音，不予投影到当前认知平面。

2. **认知来源隔离**：CAP 的认知数据来源于会话钩子，不管理也不依赖外部知识（向量数据库/API 文档/全网搜索）。外部知识属于 Agent 的背景知识，Agent 按需检索后体现在会话中——CAP 只从会话流提取切片，不做全局存储。

3. **生命周期一致**：认知与任务关联，任务完成则认知生命周期结束。不存在"所有任务的认知都堆积在一起"的情况。

**CAP 不是把所有信息存起来的系统，而是一个只保留当前目标所需信息的过滤器。**

## Q7: 什么是 Cognition Ownership（认知所有权）？

**A**: Cognition Ownership 回答的是"认知权威归谁"这个根本问题。

CAP 定义了清晰的认知边界：

- **Semantic Authority（语义权威）** 属于 Agent，不属于 Runtime
  - Agent 决定任务目标、解释语义、做出判断
  - Runtime 只执行确定性协议行为（文件操作、状态组装、生命周期管理）
  - Runtime 不做语义推理——它不"理解"任务，只"操作"任务描述

- **Cognitive Ownership（认知所有权）** 按层级划分
  - Picture 定义者拥有最终语义解释权（通常是人类或委托的 AI）
  - Agent 负责维护当前会话中的认知连续性
  - Judge Agent 独立执行验证，不从属于主 Agent 的判断

这意味着：
- Runtime 不会"理解"你在做什么，它只是忠实地记录你做了什么
- Judge Agent 的判决不受主 Agent 影响，它只读文件系统协议
- 当认知发生歧义时，谁拥有 Picture 谁就是最终仲裁者

**清晰的认知所有权划分，使 Agent 和 Runtime 各司其职——语义归 Agent，执行归 Runtime，验证归 Judge Agent。**

## Q8: 什么是 Cognitive Focus Principle（认知聚焦原则）？

**A**: Cognitive Focus Principle 是 CAP 的资源分配哲学：**认知是稀缺资源，应该只用于真正需要它的地方**。

### 认知的稀缺性

认知行为（语义推理、歧义处理、战略判断）需要上下文参与，每次执行都消耗有限上下文窗口。把它用在确定性操作（文件读写、日志记录、状态更新）上是浪费。

### 两种行为的区分

| 行为类型 | 示例 | 认知需求 | 适合谁来执行 |
|---------|------|---------|-------------|
| **认知行为** | 语义歧义判断、战略推理、目标解释 | 高 | Agent |
| **确定性操作** | 文件持久化、状态更新、版本控制 | 低 | Stable Capability Runtime |

### 委托原则

确定性操作应该委托给 Stable Capability Runtime——它不消耗认知资源，却能可靠地完成文件协议操作、状态组装、生命周期管理。

这让 Agent 的认知资源专注于：语义理解、歧义处理、创造性问题解决——那些真正需要人类级推理的任务。

**认知稀缺原则意味着：Agent 的每一次认知调用都应该是有意义的，而不是被确定性操作浪费掉的。**
