# mem0ress 规范评审报告

**评审日期：** 2026-05-12
**评审框架：** scientific-critical-thinking（规范评审扩展）
**评审维度：** 内容、解构、逻辑、颗粒度、创新性、一致性

---

## 一、内容（Content）

### 优势

- **问题诊断清晰**：数据汤困境、意图迷失、大模型之上的大模型三个结构性问题定位准确
- **核心洞察推导链完整**：四个洞察之间的依赖关系有明确说明（洞察一→洞察二→洞察三/四）
- **认知科学基础有来源说明**：目标导向行为理论、约束满足网络、事件组织记忆等概念有引用

### 缺口

1. **[P0] 状态平面"组装机制"定义缺失**
   - 5.2 节说"spec 定义组装的时机和职责边界，arch 定义具体的组装机制"
   - 但 spec 本身从未定义状态平面包含哪些字段、各字段如何从 Manifest/Session/Data Plane/Gotchas 组装
   - 影响：实现者无法知道状态平面的确切输出格式

2. **[P0] `report.md` 格式从未定义**
   - 7.3 节"决策执行规则"说"检验完成后结果写入 `report.md`"
   - 但 report.md 的模板从未出现，也没有任何字段说明
   - 影响：Tier 检验结果的存储方式完全不明确

3. **[P0] Judge Agent Manifest（`{task_id}-judge.md`）内容缺失**
   - 6.1 节说"文件名为 `{task_id}-judge.md`"
   - 附录 A 节点表说"Manifest 存储在 {task_id}-judge.md"
   - 但文件中应包含什么字段完全没有定义
   - 影响：Judge Agent 的配置和验证历史存储方式不明确

4. **[P1] `verification_history` 字段被引用但未定义**
   - 6.1 节提到"验证历史追加到其 `verification_history` 字段"
   - 但 index.md 模板和 session.md 模板都没有这个字段
   - 影响：验证历史如何存储、什么格式、查询接口是什么，完全不明确

5. **[P1] 冲突检测机制未定义**
   - 5.1 节说"若 Requirements 与 Constraints 相互矛盾，系统立即标记任务为'不可行'"
   - 但"系统"具体指什么（Agent？代码？规范本身？）以及如何检测冲突，没有定义
   - 影响：冲突检测是自动化还是人工事后检查，无法判断

6. **[P2] "认知工作区"概念未定义**
   - 3.4 节提到"Agent 获取平面后，在其认知工作区中完成目标推理与决策"
   - 认知工作区是内存空间还是临时文件，没有说明

## 二、解构（Document Structure）

### 问题

1. **[P0] spec/arch 边界存在双向泄露风险**
   - 5.2 节说"spec 定义组装的时机和职责边界，arch 定义具体的组装机制"
   - 但 spec 内部多次提到"Tier 0/1/2/3"这是 arch 实现细节
   - 建议：外部章节（如 7.3）应使用"四层检验"而非"Tier 0/1/2/3"

2. **[P1] 章节编号跳跃：第 8 章"暂无内容"**
   - 第 8 章标题存在但内容为"暂无内容"
   - 建议：删除第 8 章占位，或明确标注为规划章节

3. **[P1] 附录与正文的关系不够清晰**
   - 附录 B 模板参考是否强制要求？还是仅供参考？
   - 建议：明确附录的规范地位（normative vs informative）

### 优势

- 章节基本遵循 top-down 结构，spec 定义语义，arch 定义实现
- Mermaid 图有效辅助理解复杂概念
- FAQ 章节有效补充了规范的正文章节难以覆盖的设计决策说明

## 三、逻辑（Logic）

### 核心逻辑问题

1. **[P0] 7.3 节"只读操作"声明与"写入 report.md"实践矛盾**
   - 7.3 开头说"任务检验在...是只读操作，不执行写操作"
   - 但"决策执行规则"节说"检验完成后结果写入 `report.md`"
   - 写操作与只读声明自相矛盾
   - 这是 spec 的自我冲突：同一个章节内部两个语句不能同时为真

2. **[P0] 状态机 VERIFYING 状态与 Session 不记录状态矛盾**
   - 7.4 状态机中 VERIFYING 是有效转换状态
   - 但附录 B.1 Session 模板说明明确写"VERIFYING 为检验瞬态，不属于生命周期状态，不记录于 Session"
   - 状态机定义了 VERIFYING，但 Session 不记录 VERIFYING——那状态如何流转？

3. **[P1] Tier 3"按需触发"与"Agent 主动判断"谁先谁后**
   - 7.3 节 Tier 3 定义说"由 Agent 根据任务属性决定是否启用"
   - 但 1.3 核心解法概览图中 Tier 3 是"Judge Agent 执行器"的一部分
   - Judge Agent 是自动执行器，但 Tier 3 又说"Agent 主动判断"——主 Agent 和 Judge Agent 是什么关系？

4. **[P1] "report.md"与"验证历史"的关系不清**
   - 7.3 说检验结果写入 report.md
   - 6.1 说验证历史追加到 verification_history 字段
   - 两个存储位置是什么关系？同一份数据还是不同数据？

### 因果推理链评估

- **洞察→理念→准则的推导链**：完整且自洽
- **理念→工程实现**：部分缺失，状态平面组装机制不明确
- **状态机转换**：逻辑基本正确，但 VERIFYING 状态的使用有歧义

## 四、颗粒度（Granularity）

### 过粗（P0）

1. **状态平面输出格式未定义**
   - spec 说状态平面在 Agent 唤醒时强制挂载
   - 但具体输出什么字段、各字段格式是什么，没有定义
   - 实现者只能靠猜

2. **Judge Agent 的 prompt/指令结构未定义**
   - 附录 A 提到 Judge Agent 执行 Tier 0/1/2/3 检验
   - 但 Judge Agent 接收什么指令、输出什么格式、判定逻辑是什么，没有定义
   - 实际上 Judge Agent 可能就是 LLM，如果是 LLM，prompt 模板在哪里？

3. **manifest/index.md 的 truth source 地位与实际读取逻辑冲突**
   - 6.1 节说"Manifest 是 Picture/Requirements/Constraints 的唯一真相来源"
   - 但 5.2 节说"Picture/Requirements/Constraints 从 TaskManifest 获取，不显示在状态平面中"
   - 状态平面不显示，那 Agent 如何基于状态平面做判断？

### 过细（P2）

1. **5.1"谁来定义"表格位置不当**
   - "Picture 主要定义者是利益相关者"这类操作指导放在 spec 正文章节
   - 这更像是用户指南或最佳实践文档的内容，不是规范正文
   - 建议移至附录或用户手册

2. **Turn 编号格式 `{parent_turn}.{child_turn}` 在状态机外暴露**
   - 状态机本身不需要知道 Turn 编号
   - 编号格式属于操作约定，应在附录模板中而非状态机附近

## 五、创新性（Innovation）

### 真正创新的部分

1. **PRC 框架的完整性**：将 Picture/Requirements/Constraints 三要素与目标导向行为理论结合，有认知科学依据
2. **分形树状结构的依赖表达**：用目录深度替代数据库外键，是真正新颖的工程决策
3. **SSOT + 绝对覆写**：拒绝模糊认知合并，与传统 memory 系统的 merge 策略有本质区别

### 创新性不足的部分

1. **认知科学引用缺乏具体文献**
   - "目标导向行为理论"和"约束满足网络"只提到名称，没有作者、年份、期刊
   - 无法追溯原始来源，影响规范的可验证性

2. **"数据汤"困境是已有概念的新包装**
   - Context Collapse、熵增等概念在传统记忆系统中已有讨论
   - 规范没有说明 mem0ress 的具体解决机制与已有方案的实质差异
