# verify.md

`verify.md` 是验证协议的 Canonical 真源。每个 Task 创建时生成（空文件），随着任务执行逐步填充。

**与 task.md 的关系**：task.md 的 Constraints 和 Requirements 条目不在此重复。task.md 的验证结果字段是对 verify.md 中对应条目的引用（Reference Record），verify.md 才是 Canonical。

## 核心设计原则

1. **验证方式通过交互式对话确认，不追求预先全覆盖**
2. **验证方式和验证结论都记录在 verify.md，是 Canonical 记录**
3. **Agent 可写验证结论，执行所依据的程序由人预先验证**
4. **Tier 2（确定性验证）和 Tier 3（语义对齐）通过不同目标的人机对话确认验证方式**

## 文件结构

```markdown
# verify.md

## Constraints
## Requirements
## Picture（语义对齐）
## 验证记录
```

## Constraints

引用 task.md 中的 Constraint 条目，仅记录验证相关状态。

### 状态标记

| 标记 | 含义 |
|------|------|
| `[]` | 待讨论：尚未确认验证方式 |
| `[.]` | 已确认：验证方式已通过对话确认（由人写入） |
| `(.)` | 已通过：Verify Agent 已执行验证并通过 |
| `[×]` | 违规中：Constraint 已被违反，等待处理 |

### 格式

```markdown
### C-1: [引用 task.md 中的约束描述]

- **验证方式**: [ ] 待讨论 / [.] 对话确认
- **验证程序**: [具体命令或规则，由人验证]
- **验证结果**: [] / [.] / (.) / [×]
- **最近检查**: Turn N.M / —
- **备注**:
```

## 写入规则

1. **`[.]` 只能由人写入** — 验证程序（命令/规则）经人验证后，人才将其标记为已确认
2. **Agent 可写验证结论 `(.)` / `{.)` / `[×]`** — Agent 执行验证后写入结果，无需每次都等人确认
3. **验证记录只追加，不修改历史** — 每次检验结论追加新块
4. **Tier 3 结论记录在验证记录中** — 不在此文件定义具体语义标准

---

## 验证程序的管理

验证程序（命令/规则）是人对"这个程序是否真的能验证这个 Constraint/Requirement"的判断结果。

**程序必须经人验证**，但程序执行结果（通过/失败）可以由 Agent 写入。

流程：

```
人验证程序 → 写入 [.] + 记录验证程序内容
    ↓
Agent 执行程序 → 写入 (.) / {.} / [×]
```

## Picture（语义对齐）

引用 task.md 中的 Picture（语义成功状态）。通过人机对话确认产出是否与 Picture 对齐。

### 状态标记

| 标记 | 含义 |
|------|------|
| `[]` | 待讨论：尚未确认对齐验证方式 |
| `[.]` | 已确认：对话已确认对齐验证方式 |
| `{.}` | 已对齐：产出与 Picture 语义对齐 |
| `[×]` | 未对齐：产出与 Picture 存在语义偏差 |

### Tier 2 vs Tier 3 对话目标

- **Tier 2 对话目标**：生成确定性验证方法（可 replay 的命令/规则）
- **Tier 3 对话目标**：对任务成果进行语言判断（一次性结论，不可 replay）

### 格式

```markdown
### T3-1: [引用 task.md 中的 Picture 描述]

- **验证方式**: [ ] 待讨论 / [.] 对话确认
- **验证方式说明**: [对话确认的对齐验证方式]
- **验证结果**: [] / [.] / {.} / [×]
- **最近检查**: Turn N.M / —
- **备注**:
```
